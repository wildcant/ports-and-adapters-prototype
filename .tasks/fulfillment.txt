Fulfillment Module - In-Depth Analysis

1. Module Overview

The fulfillment module (packages/modules/fulfillment) handles shipping configuration, geographic zones,
fulfillment providers, and the actual creation/tracking of fulfillments. It's registered as
Modules.FULFILLMENT and uses a provider-based architecture to delegate actual shipping logic to external
providers.

Entry point (src/index.ts): Exports a Module() with FulfillmentModuleService and a loadProviders loader.

Linkable keys (for cross-module joins): fulfillment_id, fulfillment_set_id, shipping_option_id,
shipping_option_rule_id, fulfillment_provider_id.

---
2. Data Model Architecture

The module has 12 entities organized in a hierarchical structure:

Entity Hierarchy

ShippingProfile (grouping)
    └── ShippingOption (a shipping method)
            ├── ShippingOptionType (label, code, description)
            ├── ShippingOptionRule[] (context-based filtering rules)
            ├── ServiceZone (where it's available)
            └── FulfillmentProvider (who fulfills it)

FulfillmentSet (logical grouping tied to a location)
    └── ServiceZone (geographic availability)
            └── GeoZone[] (country/province/city/zip)

Fulfillment (an actual shipment)
    ├── FulfillmentAddress (delivery address)
    ├── FulfillmentItem[] (what's being shipped)
    ├── FulfillmentLabel[] (tracking numbers/labels)
    ├── FulfillmentProvider
    └── ShippingOption (optional reference)

3. Service Layer

FulfillmentModuleService (src/services/fulfillment-module-service.ts)

The main service (~2200 lines) extends MedusaService with auto-generated CRUD for most entities except
Fulfillment (explicitly excluded to control the exposed API).

Key design decisions:
- Uses the public/protected method pattern: public methods use @InjectManager() + @EmitEvents(),
protected _ methods use @InjectTransactionManager()
- Manually implements all Fulfillment CRUD (retrieve, list, listAndCount, create, update, delete, cancel)

4. Rule Engine (src/utils/utils.ts)

The module contains a built-in rule engine for context-based shipping option filtering:

Supported operators: in, nin, eq, ne, gt, gte, lt, lte

Rules support date comparison and numeric comparison. The isContextValid() function evaluates a context
object against rules, with an option for "all must match" (default) or "at least one must match".

Rules are validated (validateRule) and normalized (normalizeRulesValue - converts booleans to strings).

---
5. Event System (src/utils/events.ts)

The module emits events for all major operations across all entities:

- Fulfillment: created, updated
- FulfillmentAddress: created
- FulfillmentItem: created
- FulfillmentLabel: created, updated, deleted
- ShippingProfile: created
- ShippingOptionType: created, updated, deleted
- ShippingOptionRule: created, updated, deleted
- ShippingOption: created, updated
- FulfillmentSet: created, updated, deleted
- ServiceZone: created, updated, deleted
- GeoZone: created, updated, deleted

Events are emitted using moduleEventBuilderFactory and cascade - e.g., creating a fulfillment set also
emits service zone and geo zone creation events.

---
6. Provider Loading (src/loaders/providers.ts)

On startup:
1. Registers each configured provider in the DI container as fp_<provider_id>
2. Tracks provider identifiers in a shared registration
3. Syncs with database: creates new providers, enables existing ones, disables removed ones
4. Providers can have LIFE_TIME (default: SINGLETON)

---
7. GeoZone Validation

Strict hierarchical validation by type:
- country: requires country_code
- province: requires country_code, province_code
- city: requires country_code, province_code, city
- zip: requires country_code, province_code, city, postal_expression

---
8. Key Architectural Patterns

1. Provider pattern: Actual shipping logic is delegated to provider implementations; the module handles
data management and orchestration
2. Nested upsert/delete: Update operations on FulfillmentSets, ServiceZones, and ShippingOptions handle
complex nested entity management (detecting additions, removals, and updates of children)
3. Idempotent operations: cancelFulfillment checks canceled_at before executing
4. Optimistic fulfillment creation: Creates the DB record first, then calls the provider. On provider
failure, the DB record is cleaned up
5. Explicit Fulfillment control: Fulfillment is excluded from auto-generated methods - all CRUD is
manually implemented to enforce business rules (e.g., must cancel before delete, can't cancel if
shipped/delivered)
6. Context-based filtering: Shipping options can be filtered by geographic context and custom rules at
query time

Shipping Option Workflows (most complex)

createShippingOptionsWorkflow -- the most compositionally complex:
parallelize(
  validateFulfillmentProvidersStep,      // provider exists in service zone's locations
  validateShippingOptionPricesStep       // regions exist, provider can calculate
)
-> upsertShippingOptionsStep            // create options in fulfillment module
-> createShippingOptionsPriceSetsStep   // create PriceSets in Pricing module
-> parallelize(
      setShippingOptionsPriceSetsStep,   // create ShippingOption <-> PriceSet links
      emitEventStep(CREATED)
    )

updateShippingOptionsWorkflow -- similar but uses setShippingOptionsPricesStep (update prices) instead of
  creating new price sets.

deleteShippingOptionsWorkflow -- soft delete + removeRemoteLinkStep + emit event.

batchShippingOptionRulesWorkflow -- splits input into create/update/delete, runs all 3 in parallel.

Cross-Module Integration Workflows

createOrderFulfillmentWorkflow (in core-flows/src/order/workflows/):
fetch order -> validate -> fetch shipping option -> fetch reservations
-> prepareFulfillmentData (maps items to fulfillment items via inventory reservations)
-> createFulfillmentWorkflow.runAsStep
-> adjustInventoryLevelsStep (decrease stock)
-> parallelize(
      registerOrderFulfillmentStep,       // notify Order module
      createRemoteLinkStep (Order <-> Fulfillment),
      updateReservationsStep,
      deleteReservationsStep,
      emitEvent(FULFILLMENT_CREATED)
    )
-> createHook("fulfillmentCreated")

cancelOrderFulfillmentWorkflow: Reverses inventory -- creates/updates reservations, increases stock
levels. Calls cancelFulfillmentWorkflow.runAsStep last (no compensation, so it must be after all
compensatable steps).

markOrderFulfillmentAsDeliveredWorkflow: Validates fulfillment belongs to order, acquires lock on
orderId, runs markFulfillmentAsDeliveredWorkflow (which acquires its own lock on fulfillmentId), then
registerOrderDeliveryStep.

listShippingOptionsForCartWorkflow (in core-flows/src/cart/workflows/):
fetch cart -> validate required fields -> fetch sales channel stock locations
-> extract fulfillment_set_ids
-> hooks: setPricingContext, setShippingOptionsContext
-> build query with address filters (country, province, city, postal)
-> remoteQuery shipping_options with calculated_price context
-> compute insufficient_inventory per option
-> getTranslatedShippingOptionsStep

Pricing Integration Detail

The createShippingOptionsPriceSetsStep handles region-based prices by resolving region_id ->
currency_code via the Region module. Both flat and calculated options get a PriceSet (calculated gets an
empty prices array). Remote links ShippingOption <-> PriceSet are managed via
setShippingOptionsPriceSetsStep.
